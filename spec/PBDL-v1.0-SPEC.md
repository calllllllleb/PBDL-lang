# PBDL 1.0 Specification

**Status:** Draft
**Target Version:** PBDL 1.0
**Current Design Stage:** v0.1 language foundation

This document is the normative specification for PBDL. When this specification conflicts with examples, historical reports, design-rationale documents, or implementation behavior, this specification takes precedence.

## 1. Introduction

PBDL (Patient Behavior Description Language) is a declarative domain-specific language for describing patient behaviors and preferences and the contextual, evidential, and relational information required to interpret them.

PBDL provides a structured semantic contract between upstream information-producing systems and downstream applications. It is not intended to replace natural-language understanding or to embed an entire clinical reasoning system in the language core.

## 2. Scope

PBDL-Core is concerned with description and representation.

The current candidate core concepts are:

- Patient / Subject
- Behavior
- Preference
- Context
- Evidence / Provenance
- Relation

Behavior and Preference are the primary research objects of the initial redesign.

Treatment Pathway is **not** part of PBDL-Core in the initial redesign. It MAY later be considered as an extension or as an application-layer concept.

The following capabilities are outside PBDL-Core:

- clinical diagnosis
- clinical recommendation
- risk prediction
- causal inference
- knowledge-base reasoning
- LLM inference
- pathway recommendation
- workflow execution

## 3. Terminology and Conformance Language

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative conformance terms in this specification.

- **MUST** indicates an absolute requirement.
- **MUST NOT** indicates an absolute prohibition.
- **SHOULD** indicates a recommended requirement that may be departed from only with a justified reason.
- **SHOULD NOT** indicates a discouraged design choice that may be used only with a justified reason.
- **MAY** indicates an optional capability.

Normative requirements apply only where the relevant language construct has been defined. Unresolved syntax or field names marked `TODO` are not implicitly standardized by examples or placeholders.

## 4. Design Principles

### 4.1 Declarative representation

PBDL-Core MUST describe information rather than prescribe execution behavior.

### 4.2 Separation of facts and derived results

PBDL-Core MUST distinguish source-described facts from derived analysis.

PBDL-Core MUST NOT treat the following as source facts unless they are explicitly represented as externally derived artifacts:

- risk scores
- recommendations
- conflict results
- diagnoses generated by a model
- causal weights
- inferred treatment decisions

Reasoning, recommendation, prediction, and decision-making belong to external systems.

### 4.3 Explicit semantics and verifiability

PBDL is intended to support explicit semantics, machine-verifiable structure, persistence, and interoperability between upstream extraction and downstream applications.

### 4.4 Conservative clinical semantics

PBDL-Core MUST NOT imply unsupported causal relationships, treatment effects, or clinical conclusions merely through field names or default language constructs.

## 14. Relations

Relations connect explicit entities.

A Relation MUST reference defined entities. A Relation MUST NOT reference an undefined entity.

PBDL-Core does not currently define `causal_effect` as a default relation and does not provide unsupported causal weights as a default Core capability.

The normative relation vocabulary, endpoint constraints, directionality, multiplicity, and syntax remain **TODO**.

Candidate relation terms are tracked outside the normative relation vocabulary until separately frozen.

## 15. Terminology Binding

PBDL uses the following conceptual terminology-binding model:

```text
Coding {
    code
    display
    system
    optional version
}
```

Within this model:

- `code + system` carry the machine semantic identity.
- `display` is primarily for human-readable presentation.
- `version` is optional.

The concrete PBDL syntax and canonical serialization fields for `Coding` remain **TODO**.

No specific SNOMED CT, LOINC, ICD, or other medical terminology code is normative in this R0 foundation.

## 16. Semantic Constraints

The following constraints are currently normative:

1. PBDL-Core MUST distinguish source-described facts from derived analysis.
2. Behavior and Preference MUST support provenance/source traceability.
3. A Relation MUST NOT reference an undefined entity.
4. PBDL-Core MUST NOT present unsupported causal weights as source facts or default Core semantics.
5. Treatment Pathway is not a PBDL-Core concept in the initial redesign.

Additional cross-entity constraints, cardinality rules, identity rules, and validation semantics remain **TODO**.
